## What ran on Hearth’s ONNX Runtime

The following are host checks on the M4 Pro with ONNX Runtime 1.20.1 CPU, two intra-op threads, three or five timed passes after warm-up. Phone latency, memory, translation and repaint time need their own measurements.

- **PP-OCRv6 Manga** processed a synthetic 770×1080 page in 242 ms FP32 and 289 ms FP16. Both detected all nine lines, including two vertical Japanese lines, and read six exactly. Each of the other three had one kana or punctuation error. On one existing private manga page it returned 33 line boxes in 467 ms FP32 and 620 ms FP16. Both detected zero on a blank page. The test followed the author’s OpenVINO example with equivalent ONNX Runtime graph calls. The example returns lines. The publisher’s full benchmark additionally filters furigana and groups lines by reading block.
- **Parallel FP32 recognition** reduced the same 33-line page to 161 ms median and 164 ms maximum over 20 warm Mac runs, with the same boxes and text as the serial model. Under concurrent load, a six-worker run reached 215 ms maximum. [Koharu source notes and latency benchmark](koharu-latency.md)
- **PP-OCRv6 Tiny detector with Hearth’s Arabic v5 recognizer** ran through the unmodified production `PaddleOcr` C++ class. Both detector versions returned all four Arabic and all four English lines on a synthetic bilingual screenshot. Median latency was 216.5 ms with v5 and 217.4 ms with v6. The four English outputs matched. One Arabic output differed in the raw CTC stream. Using v6 would reduce this pair’s download from 12.83 MB to 9.78 MB. The test does not support a speed or accuracy upgrade claim.
- **Baberu INT4/INT8** ran all three published graphs. Four synthetic crops took about 307–332 ms per crop warm. It read an English line and a vertical Japanese crop exactly, omitted one Japanese punctuation mark and misread characters in the Chinese crop. Compare it on real speech bubbles before treating these printed crops as an accuracy estimate.

## Fit with Hearth

Hearth’s current Android general OCR uses 4.83 MB of shared PP-OCRv5 detector weights plus a script reader. The Arabic and English reader is already 8.00 MB and preserves both scripts in one model. Desktop’s manga reader shares the pinned manga artifacts. Automatic manga uses 127.72 MB of weights, Koharu segmentation uses 276.16 MB, and segmentation with neural cleanup uses 483.64 MB. [Hearth’s Koharu integration and host results](../koharu-integration.md)

Koharu’s November 9 revision defaults to RF-DETR Seg 2XL, PaddleOCR-VL 1.6 and LaMa. Its exact default OCR GGUF and vision projector total 1,817,539,616 bytes. Hearth already uses pinned ONNX exports for the RF-DETR and LaMa stages and keeps the smaller Manga OCR recognizer. Koharu also has a Baberu adapter using its larger safetensors export. [Koharu configuration](https://github.com/koharu-rs/koharu/blob/8047c8b37a28f112fbf09dcf19436350b40a93ad/crates/koharu-pipeline/src/config.rs) · [OCR export](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6-GGUF/tree/511b09642bb324401f15f97cc23bc67e8f0a291d)

For a compact manga reader, use the v0.3 FP32 graphs first. They use float32 image tensors and ordinary CTC, so the ONNX session and bounded decode code can be shared. The current general reader only handles horizontal crops, enforces its own thresholds and outputs axis-aligned rectangles. Add the manga-specific vertical rotation and DB detection profile, then group lines into the correct bubble before translation. The 19,055-output vocabulary consists of blank, 19,053 source entries and space. FP16 requires float16 I/O support and took longer on this CPU. The source card cites [Manga109-s](https://huggingface.co/datasets/hal-utokyo/Manga109-s) for training data. Preserve the dataset attribution and keep the source images out of the app.

Acceptance fixtures should score exact match and CER by orientation, furigana, stylized text and language. Compare bubble coverage, reading order and untranslated regions against the same images through current Fast and Koharu. Time first outline, first readable bubble, full page and peak memory on Android and desktop. Keep the existing compact and Koharu choices during that comparison. The current release change retains a successful compact preview when the quality pass finds no readable text. These candidate model weights are research inputs and do not appear in the release model library.
